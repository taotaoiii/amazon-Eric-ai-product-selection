# 锚点校准方法

> 本文件不定义任何阈值，只讲**怎么把 `anchors.yaml` 里的 `calibrated: false` 变成 `true`**。

## 一、为什么需要校准

`anchors.yaml` 里的锚点全是**示例口径**。它们来自公开的方法论文章和同行经验，
不是你类目的实测数据。直接拿来用会出现两种情况：

- 阈值过松 → 什么品都过筛，等于没筛；
- 阈值过严 → 什么品都筛掉，你会以为"这个类目没机会"。

**锚点的作用是把你脑子里的判断力固化下来。所以校准的原材料不是公式，是你自己的成败案例。**

## 二、回测法（推荐）

### 2.1 准备案例

收集 **3–5 个你亲身经历过、结果已知**的选品案例。最好成败都有。

每个案例需要记录（用机会卡的 `metrics` 字段即可）：

- 当时的售价、类目、TOP10 平均评论数、类目平均评分、FBA 卖家数
- 当时的 Break-even ACoS、净利率
- MOQ、生产周期
- **最终结果**：赚钱 / 亏钱 / 打平

**没有 3 个案例就先别校准。** 用 1 个案例拟合出来的阈值，只会让你在下一次更自信地犯错。

### 2.2 跑回测

用 `scripts/score.py` 对这 3–5 个案例逐个打分：

```bash
cd amazon-ai-product-selection-v2
python scripts/score.py --anchors config/anchors.yaml --input case-001.json
```

也可以批量比较：

```bash
python scripts/pool.py rank --pool pool/ --anchors config/anchors.yaml
```

### 2.3 看结果

理想情况：**赚钱的案例分数明显高于亏钱的案例**。

三种结果对应三种动作：

| 结果 | 说明 | 动作 |
|---|---|---|
| 分数能分开成败 | 锚点有区分度 | 把相关锚点 `calibrated` 改为 `true` |
| 分数分不开 | 锚点对这个类目没有区分度 | 换指标，或调整区间 |
| 全都很高或全都很低 | 区间选得不对 | 按你案例的实际分布重新定上下界 |

### 2.4 重新定区间

区间的两个端点这样定：

- **下界** = 你案例里"勉强还能接受"的那个值
- **上界** = 你案例里"最好见过的"那个值（或你生意上够得着的上限）

不要用理论极值。用你真见过的数。

## 三、调整锚点的规矩

1. **一次只调一个锚点**，调完重跑回测。同时调三个，你分不清是哪个起了作用。
2. **必须更新 `last_reviewed`**。
3. **必须更新 `basis`** ——写清楚"我按自己 N 个案例校准过"。
4. **通过回测的才改 `calibrated: true`**。没回测就改 true，等于自欺。

## 四、政策变化怎么应对

有些锚点会因为平台规则变化而整体失效。这类信息写在锚点的 `caveat` 字段里。

**已知的一例**：

> `anchors.yaml#hard_filters.top10_avg_reviews_max`
> —— 2026-02-12 起亚马逊变体评论拆分规则生效（2026-05-31 完全生效），
> 导致单个 listing 的评论数系统性下降。
> 老口径下的"TOP10 平均评论数低于某值 = 蓝海"会**系统性误报为蓝海**。

处理步骤：

1. **回前台抽样复核**：手动看 5–10 个该类目 listing 的实际评论数。
2. **对比锚点值**：样本明显低于锚点时，说明阈值偏高了。
3. **重定阈值** → 更新 `last_reviewed` 与 `basis`。
4. 在 `caveat` 里记录这次调整的原因。

**没做第 1 步之前，不要动这个锚点。** 前台抽样是唯一可信的核对手段。

## 五、什么时候重新校准

- 换类目、换站点：**必须**重新校准。
- 平台政策变化：按第四节处理。
- 每季度：**至少**跑一次回测，即使没有新案例也检查一遍。
- 回测显示分不开成败：如实记录，**不要硬调**。

> **硬调锚点去拟合历史，只会让你在下一次选品时更自信地犯错。**
